# 実寸法師(.tdf)バイナリ形式の解析メモ

2026-09-11、YK-AB01(普通梁・柱詳細図)・WR-1G-1(斜め梁・大梁詳細図)の2ファイルの
実機解析で判明した内容。公式仕様書は存在しないため、あくまで実データからの
逆算であり、未知のレコード種別・例外パターンが存在する可能性がある。

## 基本方針

- すべて読み取り専用の解析。書き込みは一切行わない。
- レコードはオフセットベースの可変長形式。各レコードの先頭4バイトに
  `0x80000000 | レコード長` という形の符号なしサイズヘッダーが入っていることが多い
  (int32として読むと負の値になる)。
- 座標系はCADの実座標(mm)。Y軸は下方向が負。

## 1. テキスト要素

マーカー4バイト = `00 N (2*N) 00`。Nは1〜63の範囲で、テキストの機能種別ごとに
異なる値を取る(固定値ではない)。3バイト目が常に「2*N」になるという規則性で
汎用的に検出する。

```
[pre_field:4] [X:double][Y:double][H:double][W:double][rot:double]
[pad:4] [id_field:4] [marker:4] [val1:4=textlen+8][val2:4] [text: cp932, val1-8バイト]
```

ヘッダー長は52バイト(pre_fieldからid_fieldまで、マーカー手前まで)。
`rot`はラジアン。0なら水平配置、斜め梁の梁本体に付随する注記はこの値が
梁の傾き角そのものになる(例: -2.048°)。

`pad`フィールドは常に0ではない。寸法値テキストなど、寸法オブジェクトに
紐づくテキストは非ゼロの共通値(例: 336860180)を持つことがある。同じ値が
複数ファイルにまたがって出現するため、ファイル固有のオフセットではなく、
寸法オブジェクトの種別を示す固定的なコードだと推測される。ただし今回の
抽出ロジックではこのフィールドは使っていない。

### 本体と参照

同じ文字列が図面内に複数回現れることがある(例: KEY PLAN上の位置マーカーと
部材情報テーブルの両方に同じ製品マークが描かれる)。バイナリ上は「本体」
(実際にテキストバッファを持つレコード、`text`のデコードに成功する)が1つと、
「参照」(本体のid_fieldを指すだけで自分ではテキストを持たない、`text`の
デコードは失敗しNoneになる)が複数、という構造。参照レコードも自分自身の
X/Y/H/W/rotは持っている。

`id_field`が一致するレコード同士が同じ文字列を指す。参照レコードの実際の
文字列は、同じid_fieldを持つ本体レコードから解決する
(`tdf_binary.TdfData.resolve_text`)。

## 2. 直線要素

```
[size=0x80000038(56)] [val=1] [type:2][subtype:2] [ref:4]*3
[x1:double][y1:double][x2:double][y2:double]
```

56バイト固定長。`val`が1のものだけが直線。

`ref0`(オフセット+8の4バイト)は**「実寸法師が自動生成する主要な寸法線・製品長さの線」であれば必ず`3`**という値を持つ。これに対し、ボルトピッチ・リブ・ハッチング等、後から個別に描き足された注記線は`ref0`が(おそらく描画順の連番のような)大きい値になる。2026-09-14、鳥取現場図面(EA1-1G-xxシリーズ)の検証で、`ref0==3`のライン本数を「長さ」判定スコアリングの最優先項目にしたところ、14ファイル15行全てで正解と一致した(詳細は5節参照)。

`ref1`(オフセット+12)は同一ファイル内でほぼ全ての線が共有する値(レイヤー的なもの、"GEN"という名前のレイヤーレコードに繋がる)で、`ref0`のような使い分けは無い(白色/色分けの判別には使えなかった)。`ref2`/`ref3`(オフセット+16,+20)は前後のライン要素へのオフセットを指すリンクリストと見られる。

## 3. 円弧要素(2レコード1組)

「中心+半径」レコードの直後(オフセット+48)に「開始角・終了角」レコードが続く。

```
[size=0x80000030(48)] [val=2] [ref:4]*4
[cx:double][cy:double][r:double]
--- 直後 ---
[size=0x80000020(32)] [type:4][subtype:4] [ref:4]
[a1:double(rad)][a2:double(rad)]
```

角度ペアの2つのdoubleは、角度レコード先頭から数えて**+16バイト目**から
始まる(+24バイト目ではない。ここでオフセット計算を間違えると全角度が
壊れて出る、要注意)。

### 長丸(スタジアム形状)の検出

実寸法師の「長丸」機能(角の丸い長方形の囲み枠)は、直線2本(上辺・下辺)+
円弧2つ(左右の半円)で構成される。円弧のペアは

- 半径が一致する
- 開始角の差がちょうど180°(片方が「右向きに開く」、もう片方が
  「左向きに開く」)

という関係を持ち、2つの円弧の中心の中点が、長丸の中心＝内側のテキストの
表示位置と一致する。この性質は図面が回転(斜め梁)していても保たれる
(開始角の差が180°という「相対関係」は回転不変)。

## 4. 製品情報テーブル

`製品マーク | 設計符号 | サイズ | 本数(N台) [| 重量(N.Nkg)]` という横並びの
テキスト列が、pad=0の通常テキスト(rot=0)として描画されている。列の間隔・
本数セルとの整列は図面によって微妙に異なる(重量セルだけ本数セルとYが
数十単位ずれることがある)ため、抽出時は座標の完全一致ではなく許容誤差を
持たせている。

サイズ列は`H-`, `[-`, `L-`, `BOX`, `角`などで始まる断面表記。本数列は
`unicodedata.normalize("NFKC", text)`で全角/半角ゆれを吸収した上で
`^[0-9]+台$`にマッチするセル。

図番はタイトル欄にあり、英字始まりの英数字+ハイフンのみの文字列
(`^[A-Za-z][A-Za-z0-9\-]{2,19}$`)のうち、最も文字高さが大きいもの、という
ヒューリスティックで推定している。数字始まりの図番(社内シート番号などと
紛らわしい)は意図的に除外している。

**2026-09-14改訂**: 上記の「文字高さ最大」だけでは、製品テーブルの
「設計符号」欄がたまたま図番と同じ文字高さで書かれている場合に誤検出する
ことが判明した(EA1-1G-14で発覚。設計符号`CG1400A`と図番`EA1-1G-14`が
両方h=120で同点になり、内部データ順で偶然`CG1400A`が先に採用されていた)。

そこで、タイトル欄に必ずある「図面番号」という4文字のラベル(「図」「面」
「番」「号」が単独の1文字テキストとして、同じY・等間隔でX方向に連続して
並んでいる箇所)をまず探し、そのラベルの近く(Y座標の差500mm以内)にある
候補の中から、ラベルにX方向で最も近いものを図番として採用するように
変更した。ラベルが見つからない場合や近くに候補が無い場合のみ、従来通り
文字高さ最大の方式にフォールバックする。48ファイルで検証し、EA1-1G-14
以外の47ファイルは結果が変わらないことを確認済み。

## 5. 「長さ」の判定(製品ごとの実長寸法値)

製品マーク〜本数セルのX範囲、Yがそのテーブル行より上(CAD座標でプラス方向)
にある数値テキスト群の中から、以下の手順で1つに絞り込む。

1. 各テキストの座標を、そのテキスト自身の`rot`で回転補正した座標
   (xr, yr)を求める。
2. **絞り込み前の全テキストから**、図面全体の主軸方向(rotの最頻値)を
   推定する(3のフィルタ後に計算すると、たまたま小さい値ばかりが多い
   向きのテキストが削られて少数派の向きに引っ張られることがある。
   2026-09-14、夢前現場図面WA1-1G-02で発覚し、フィルタより前に
   計算する順序に修正した)。
3. この時点で集めた数値の最大値の1/5未満の値は、候補から除外する
   (取付ピッチ・ボルト間隔等の小さい寸法が、後段のスコアリングで
   誤って「長さ」として選ばれてしまうのを防ぐため。2026-09-14、
   鳥取現場図面(EA1-1G-xxシリーズ)の検証で追加したルール)。
4. 出現回数が5回以上、または回転補正後の座標(向きに応じてxr/yrいずれか)が
   近い値を持つテキストが3個以上ある場合、それは「取付ピッチ・ボルト間隔」
   などの繰り返し寸法とみなして候補から除外する。
5. ただし除外された値でも、**他の系列の合計**(取付ピッチの累積など)と
   一致するなら候補として復活させる(全長は「内訳の合計」と一致するのが
   通例のため)。
6. 300以下の値は候補から除外する(小さすぎる値はボルト間隔等)。
7. ただしステップ4で除外された値でも、**`ref0==3`(主要な寸法線を示す
   マーカー、2節参照)の一致直線が1本でもあれば無条件で候補に復活させる**
   (2026-09-14追加。鳥取現場図面EA2-1G-11で、真の長さの数値が偶然
   他の内訳数値と同じY座標の行に並んでいたために「取付ピッチの繰り返し」
   と誤除外されていた問題を受けて追加。`ref0==3`は確実な証拠なので、
   ピッチ除外ロジックより優先する)。
8. 残った候補について、図面の主軸方向に沿い長さが完全一致する直線を全て集め、
   そのうち**ライン要素の`ref0`が`3`であるものの本数(C)を最優先スコア**とする。
   同点の場合は(A)一致直線の総本数、さらに同点なら(B)他系列合計との一致回数、
   の順で比較し、最終的にCが最多の候補を「長さ」として採用する
   (2026-09-14追加。`ref0==3`は実寸法師が自動生成する主要な寸法線を示す
   マーカーで、ボルトピッチ・リブ等の手動追加線や通り芯スパン線は`ref0`が
   別の値になるため、この一手で両方の誤検出パターンを解消できた。
   詳細は2節参照)。

この手順は普通梁(回転なし)・斜め梁(回転あり)の両方で、実測値と一致する
ことを2ファイルで確認済み(2026-09-11時点)。2026-09-14、鳥取現場図面
(EA1-1G-xxシリーズ、14ファイル・15行)で、ステップ3(1/5フィルタ)+
ステップ8(`ref0==3`優先スコアリング)の組み合わせにより、ユーザー提供の
正解データと全行(長さ)が一致することを確認済み。夢前現場図面(WA1-1G-xx
シリーズ)の検証では、ステップ2(主軸方向推定)をステップ3(1/5フィルタ)
より前に計算する順序に修正する必要があった(WA1-1G-02で発覚)。

## 6. 「左継手・右継手」の判定(2026-09-14に全面改訂)

1. 長丸(4節)の中心座標をすべて検出し、中心に対応するテキストを継手候補
   とする。
2. **候補テキストが`^GJ`(GJで始まる)というパターンに一致するものだけを
   対象にする**。継手コードは図面内で必ず`GJ`始まり(`GJ140BA`,`GJW160B`等)
   であり、`P441`・`TB888`・`B34`等の無関係な部材記号はこのパターンに
   一致しないため、「N台」パターンと同様に文字列そのものだけで確実に
   区別できる(製品マークがどう抽出できたかの説明と同じ理屈。詳細は4節参照)。
3. 候補の座標を、5節で求めた主軸方向で回転補正する。
4. 製品マーク自身のX座標(回転補正後)に最も近いGJ候補を左継手、
   本数セル自身のX座標(回転補正後)に最も近いGJ候補を右継手の候補とする。
5. その最寄り候補との距離が「長さ×0.6」を超える場合は、その側に継手が
   無い(現場溶接等)とみなしNoneを返す。継手はこの長さ範囲の内側にある
   とは限らず、外側に対称にはみ出すこともある(実測で確認済み。梁端部の
   継手代と思われる)ため、ある程度の許容を持たせている。

該当側にGJコードが見つからない場合はNoneを返し、Excel出力(`extract_to_excel.py`)
でもそのまま空欄として出力する(2026-09-14、ユーザー確認済みの仕様)。

**旧ロジック(〜2026-09-14)の問題点**: 長丸候補をY座標の近さだけでペアに
グルーピングし、そのペアのX範囲が「長さ」に最も近いものを機械的に採用
していたため、継手が片側にしかない図面(EA1-1G-13/EA1-1G-14で確認)で、
無関係な部材記号(`P441`等)同士のペアをたまたま長さと一致するという理由で
誤って両側の継手として採用してしまっていた。`GJ`パターンによる事前絞り込みと、
製品自身のマーク/本数セル座標を基準にした「最寄り判定」に変更したことで解消。

## 7. 「種別(普通梁/斜め梁)」列(2026-09-14追加)

`extract_to_excel.py`のK列に、5節で求めた`main_axis_deg`から判定した
種別を出力する。`main_axis_deg % 90`が±2度以内なら図面の縦横に沿う向き
=「普通梁」、それ以外の半端な角度なら「斜め梁」とする(0度・90度は単に
ページ上での描画の向きの違いであり、部材自体が傾いているわけではない
ため、どちらも「普通梁」扱いになる。実際に傾いた部材は`-2.048度`のような
半端な角度になる。2026-09-11検証時の`WR-1G-1`(斜め梁)がこの判定基準の
根拠)。長さが判定できずmain_axis_deg自体が無い場合は空欄を出力する。

## 既知の限界

- 検証は当初2ファイル(普通梁1種・斜め梁1種)+鳥取現場図面EA1(14ファイル
  15行)+EA2(16ファイル18行)の計32ファイルのみ。EA1は長さ・継手とも
  正解データと全行一致、EA2はユーザー指摘のEA2-1G-11(2880)を含め
  目視で異常なしを確認済み(2026-09-14)。
- 製品情報テーブルの列構成(重量列の有無、列順)が異なる図面フォーマット
  への対応は未検証。
- 継手コードが`GJ`以外のプレフィックスで表現される図面フォーマットが
  存在する場合は未対応(6節のパターンマッチが空振りし、両側とも「無し」
  になる)。他社図面等で試す際は要確認。
- (解消済み)「長さ」判定で通り芯スパンやボルトピッチが誤って選ばれる
  問題は、ライン要素の`ref0==3`優先スコアリング(2節・5節参照)で解消した。
  ライン要素の色情報(白色の線のみを対象にする案)も並行調査したが、
  ラインレコード自体には単純な色フィールドが見当たらず、`ref0`の方が
  有効な手がかりだった。
- (解消済み)継手が片側にしかない図面で誤ったペアを採用する問題は、
  継手コードの`GJ`プレフィックスパターンマッチ+製品自身のマーク/本数
  セル座標基準の最寄り判定(6節)で解消した。
